# Noomori Recipe Database Specification

**Status:** MVP Source of Truth
**Version:** 1.4
**Scope:** Recipe persistence, ownership, structured content, preparation/cooking time, servings, nutrition, source attribution, and image storage.

---

# 1. Core Domain Rule

A recipe is always owned by a user.

```text
Profile
   │
   │ owns
   ▼
Recipe
```

A household does **not** own recipes.

Household access is represented separately:

```text
Recipe
   │
   ▼
household_recipe_shares
   │
   ▼
Household
```

Therefore, the `recipes` table MUST NOT contain `household_id`.

---

# 2. Canonical Database Schema

```sql
create table public.recipes (
  id uuid primary key default gen_random_uuid(),

  owner_user_id uuid not null
    references public.profiles(id)
    on delete cascade,

  title text not null
    check (
      char_length(trim(title)) between 1 and 200
    ),

  description text,

  image_path text,

  ingredients jsonb not null default '[]'::jsonb
    check (
      jsonb_typeof(ingredients) = 'array'
    ),

  instructions jsonb not null default '[]'::jsonb
    check (
      jsonb_typeof(instructions) = 'array'
    ),

  servings integer not null default 1
  check (servings > 0),

  prep_time_minutes integer
    check (
      prep_time_minutes is null
      or prep_time_minutes >= 0
    ),

  cook_time_minutes integer
    check (
      cook_time_minutes is null
      or cook_time_minutes >= 0
    ),

  nutrition_per_serving jsonb
    check (
      nutrition_per_serving is null
      or jsonb_typeof(nutrition_per_serving) = 'object'
    ),

  source_type text not null default 'my_recipe'
    check (
      source_type in (
        'my_recipe',
        'family',
        'website'
      )
    ),

  source_person_name text,

  source_url text,

  created_at timestamptz not null default now(),

  updated_at timestamptz not null default now(),

  constraint recipes_source_details_check
    check (
      (
        source_type = 'my_recipe'
        and source_person_name is null
        and source_url is null
      )
      or
      (
        source_type = 'family'
        and nullif(trim(source_person_name), '') is not null
        and source_url is null
      )
      or
      (
        source_type = 'website'
        and source_person_name is null
        and nullif(trim(source_url), '') is not null
      )
    )
);
```

Canonical index:

```sql
create index idx_recipes_owner_created_at
on public.recipes (
  owner_user_id,
  created_at desc
);
```

# 3. Existing Database Schema Changes

The current `recipes` table already exists and currently contains no recipe data.

Therefore, no data migration is required.

Add the Family attribution field:

```sql
alter table public.recipes
add column source_person_name text;
```

Remove the previous source constraints:

```sql
alter table public.recipes
drop constraint if exists recipes_source_url_check;

alter table public.recipes
drop constraint if exists recipes_source_type_check;
```

Replace the `source_type` default:

```sql
alter table public.recipes
alter column source_type drop default;

alter table public.recipes
alter column source_type set default 'my_recipe';
```

Add the canonical source types:

```sql
alter table public.recipes
add constraint recipes_source_type_check
check (
  source_type in (
    'my_recipe',
    'family',
    'website'
  )
);
```

Add the source-detail invariant:

```sql
alter table public.recipes
add constraint recipes_source_details_check
check (
  (
    source_type = 'my_recipe'
    and source_person_name is null
    and source_url is null
  )
  or
  (
    source_type = 'family'
    and nullif(trim(source_person_name), '') is not null
    and source_url is null
  )
  or
  (
    source_type = 'website'
    and source_person_name is null
    and nullif(trim(source_url), '') is not null
  )
);
```

# 4. `id`

```text
Type: UUID
Required: Yes
Generated by: Database
```

Unique identifier for the recipe.

---

# 5. `owner_user_id`

```text
Type: UUID
Required: Yes
Foreign Key: public.profiles(id)
Delete behavior: CASCADE
```

Identifies the user who owns the recipe.

The backend MUST derive this value from the authenticated identity.

```text
JWT
 ↓
claims.sub
 ↓
profile.id
 ↓
recipes.owner_user_id
```

The mobile client MUST NOT be trusted to choose an arbitrary `owner_user_id`.

Recipe ownership is independent from household membership.

---

# 6. `title`

```text
Type: TEXT
Required: Yes
Min length after trim: 1
Max length after trim: 200
```

Whitespace-only titles are invalid.

---

# 7. `description`

```text
Type: TEXT
Required: No
Default: NULL
```

`NULL` means no description has been provided.

---

# 8. `image_path`

```text
Type: TEXT
Required: No
Default: NULL
```

The database stores the Supabase Storage object path.

It MUST NOT store the image binary or an expiring signed URL.

Canonical path:

```text
recipes/{owner_user_id}/{recipe_id}/{image_id}.webp
```

Example:

```text
recipes/U001/R001/8a0971e2.webp
```

Every upload receives a new `image_id`. Replacements MUST use a new path rather
than overwriting a fixed `cover.webp` object. This keeps image identity stable
and lets the rendering cache invalidate naturally when the active image changes.

The backend may generate an `image_url` for API consumers.

```text
Database
→ image_path

API Response
→ image_url
```

Recipe images MUST use the private `recipe-images` Supabase Storage bucket.

# 9. `ingredients`

```text
Type: JSONB
Required: Yes
Default: []
Top-level type: Array
```

Canonical structure:

```json
[
  {
    "title": "For the sauce",
    "items": [
      {
        "name": "Coconut milk",
        "quantity": 200,
        "unit": "ml",
        "note": null
      }
    ]
  }
]
```

Sectionless ingredients still use an unnamed section:

```json
[
  {
    "title": null,
    "items": [
      {
        "name": "Egg",
        "quantity": 2,
        "unit": null,
        "note": null
      }
    ]
  }
]
```

Array position determines ordering.

---

# 10. Ingredient Contract

```python
class IngredientItem(BaseModel):
    name: str
    quantity: float | None = None
    unit: str | None = None
    note: str | None = None


class IngredientSection(BaseModel):
    title: str | None = None
    items: list[IngredientItem]
```

PostgreSQL validates the top-level JSON type.

Pydantic validates its nested structure.

# 13. `servings`

```text
Type: INTEGER
Required: No
Default: 1
```

Semantics:

```text
NULL
→ Not set

4
→ Recipe yields approximately 4 servings
```

Missing servings MUST NOT automatically become `1`.

# 14. `prep_time_minutes`

```text
Type: INTEGER
Required: No
Default: NULL
Unit: Minutes
Constraint: >= 0 when present
```

Semantics:

```text
NULL
→ Not set

0
→ Explicitly 0 minutes

> 0
→ Explicitly provided prep time
```

Persisted representation is always:

```text
INTEGER minutes | NULL
```

Recommended Pydantic field:

```python
prep_time_minutes: int | None = Field(
    default=None,
    ge=0,
)
```

→ Not set

→ Explicitly 0 minutes

# 16. Recipe Time Rules

Preparation and cooking time are stored independently.

```text
prep_time_minutes
→ preparation duration

cook_time_minutes
→ cooking duration
```

`NULL` and `0` MUST retain different meanings.

```text
NULL
→ unknown / not selected

0
→ explicitly zero minutes
```

Duration formatting belongs to the presentation layer.

The database MUST NOT persist:

```text
"10 minutes"
"1 hour"
"Not set"
```

---

# 17. Total Time

`total_time_minutes` is NOT stored during MVP.

When both durations are known:

```text
total_time_minutes
=
prep_time_minutes
+
cook_time_minutes
```

If one duration is `NULL`, the missing duration MUST NOT implicitly become `0`.

---

# 18. `nutrition_per_serving`

```text
Type: JSONB
Required: No
Default: NULL
Top-level type: Object
```

Nutrition represents one serving.

Example:

```json
{
  "calories_kcal": 420,
  "protein_g": 31,
  "carbs_g": 18,
  "fat_g": 24,
  "fiber_g": 3,
  "sugar_g": 5,
  "sodium_mg": 620
}
```

Recommended backend model:

```python
class Nutrition(BaseModel):
    calories_kcal: float | None = Field(default=None, ge=0)
    protein_g: float | None = Field(default=None, ge=0)
    carbs_g: float | None = Field(default=None, ge=0)
    fat_g: float | None = Field(default=None, ge=0)
    fiber_g: float | None = Field(default=None, ge=0)
    sugar_g: float | None = Field(default=None, ge=0)
    sodium_mg: float | None = Field(default=None, ge=0)
```

# 19. Recipe Source Model

Recipe source describes **where the recipe originally comes from**, not how the recipe was entered into Noomori.

The canonical source options correspond directly to the product UI:

```text
My Recipe
Family
Website
```

Database representation:

```text
my_recipe
family
website
```

This concept MUST remain separate from recipe ownership.

For example:

```text
Owner
→ current Noomori user

Source
→ Grandma
```

A recipe received from a family member still belongs to the Noomori user who created or saved it.

---

# 20. `source_type`

```text
Type: TEXT
Required: Yes
Default: my_recipe
```

Canonical values:

```text
my_recipe
family
website
```

No other source values are part of the MVP domain.

---

## `my_recipe`

UI label:

```text
My Recipe
```

Represents a recipe attributed to the current user.

Required representation:

```text
source_type = my_recipe
source_person_name = NULL
source_url = NULL
```

Example:

```json
{
  "source_type": "my_recipe",
  "source_person_name": null,
  "source_url": null
}
```

---

## `family`

UI label:

```text
Family
```

Represents a recipe originating from a family member.

The UI MUST collect:

```text
From whom?
```

This is persisted in:

```text
source_person_name
```

Example:

```json
{
  "source_type": "family",
  "source_person_name": "Grandma",
  "source_url": null
}
```

`source_person_name` is attribution text.

It is NOT:

```text
a Noomori user ID
a household member ID
a profile foreign key
```

The source person does not need to have a Noomori account.

---

## `website`

UI label:

```text
Website
```

Represents a recipe originating from a website.

The UI MUST collect a URL.

Representation:

```json
{
  "source_type": "website",
  "source_person_name": null,
  "source_url": "https://example.com/chicken-curry"
}
```

---

# 21. `source_person_name`

```text
Type: TEXT
Required: Conditional
Default: NULL
```

Required when:

```text
source_type = family
```

Otherwise it MUST be `NULL`.

Examples:

```text
"Mom"
"Grandma"
"Dad"
"Aunt Sarah"
```

Invalid:

```text
source_type = family
source_person_name = NULL
```

Invalid:

```text
source_type = family
source_person_name = ""
```

Whitespace-only values are also invalid.

---

# 22. `source_url`

```text
Type: TEXT
Required: Conditional
Default: NULL
```

Required when:

```text
source_type = website
```

Otherwise it MUST be `NULL`.

Valid:

```text
source_type = website
source_url = https://example.com/recipe
```

Invalid:

```text
source_type = website
source_url = NULL
```

Invalid:

```text
source_type = website
source_url = ""
```

Whitespace-only values are also invalid.

URL structure SHOULD additionally be validated by Pydantic.

---

# 23. Source Detail Matrix

| Source    | `source_type` | `source_person_name` | `source_url` |
| --------- | ------------- | -------------------- | ------------ |
| My Recipe | `my_recipe`   | `NULL`               | `NULL`       |
| Family    | `family`      | Required             | `NULL`       |
| Website   | `website`     | `NULL`               | Required     |

These combinations are canonical.

Any combination outside this matrix MUST be rejected.

# 24. Source Database Invariant

The database enforces the source-detail combinations through:

```sql
constraint recipes_source_details_check
check (
  (
    source_type = 'my_recipe'
    and source_person_name is null
    and source_url is null
  )
  or
  (
    source_type = 'family'
    and nullif(trim(source_person_name), '') is not null
    and source_url is null
  )
  or
  (
    source_type = 'website'
    and source_person_name is null
    and nullif(trim(source_url), '') is not null
  )
)
```

This prevents invalid states such as:

```text
Family + website URL
Website + family attribution
My Recipe + source details
Family without person
Website without URL
```

---

# 25. Source vs Ownership

`source_person_name` MUST NOT be confused with `owner_user_id`.

Example:

```text
Recipe:
Grandma's Rendang

owner_user_id
→ current Noomori user

source_type
→ family

source_person_name
→ Grandma
```

The current user owns the database recipe.

`Grandma` represents provenance only.

---

# 26. Source vs Import Method

`source_type` describes provenance.

It MUST NOT be used to describe technical ingestion methods such as:

```text
manual entry
text parsing
URL parser
Instagram caption import
```

Those are separate concepts.

If Noomori later needs to track ingestion method, it SHOULD introduce a separate field such as:

```text
import_method
```

instead of overloading `source_type`.

---

# 27. Timestamps

## `created_at`

```text
Type: TIMESTAMPTZ
Required: Yes
Default: now()
```

## `updated_at`

```text
Type: TIMESTAMPTZ
Required: Yes
Default on INSERT: now()
```

`default now()` does not automatically update after an `UPDATE`.

Noomori MUST use one consistent update mechanism.

Preferred:

```text
PostgreSQL BEFORE UPDATE trigger
→ updated_at = now()
```

# 29. Household Relationship

The `recipes` table MUST NOT contain:

```text
household_id
household_role
shared
is_shared
```

Sharing belongs to:

```text
household_recipe_shares
```

Conceptually:

```text
profiles
   │
   │ owns
   ▼
recipes
   │
   │ shared through
   ▼
household_recipe_shares
   │
   ▼
households
```

---

# 30. Personal-First Rule

Every recipe starts as personally owned.

```text
Create Recipe
     ↓
Current User Owns Recipe
     ↓
Optional Explicit Share
     ↓
Household Access
```

Sharing never transfers ownership.

      ↓
FastAPI
      ↓

# 33. Core Recipe Invariants

1. Every recipe has exactly one user owner.
2. A household never owns a recipe.
3. Recipes are personal by default.
4. Sharing is independent from ownership.
5. Ingredients use canonical section-based JSON.
6. Instructions use canonical section-based JSON.
7. Sectionless content uses `title: null`.
8. Array position determines ordering.
9. `servings = NULL` means servings are not set.
10. `prep_time_minutes = NULL` means prep time is not set.
11. `cook_time_minutes = NULL` means cook time is not set.
12. Recipe durations are stored as integer minutes.
13. Unknown durations MUST NOT implicitly become zero.
14. Nutrition represents one serving.
15. Recipe images live in object storage.
16. PostgreSQL stores `image_path`, not signed URLs.
17. Recipe source describes provenance, not ownership.
18. Canonical source types are `my_recipe`, `family`, and `website`.
19. `family` requires `source_person_name`.
20. `website` requires `source_url`.
21. `my_recipe` has neither `source_person_name` nor `source_url`.
22. `source_person_name` is free-text attribution, not a user relationship.
23. Backend authentication determines `owner_user_id`.
